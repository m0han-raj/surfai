The problem with raw HTML

A typical e-commerce page ships several hundred kilobytes of markup. Most of it is layout scaffolding, analytics hooks, inline styling and framework bookkeeping. Almost none of it describes what a person can actually do on the page.

Feeding that markup to a language model is expensive and, more importantly, ineffective. The signal a planner needs -- where the search box is, which control filters by price, which links lead to results -- is buried under noise that actively competes for the model's attention.

The question is not how much of the page a model can read. It is how little it needs to read in order to act correctly.

A semantic approach

A semantic extractor walks the document once and keeps only interactive and structural elements: inputs, buttons, links, selects, headings and labels. Each is reduced to the handful of facts that matter for acting on it -- its kind, its accessible name, whether it is visible, and whether it is currently usable.

Accessible naming does most of the work. An element's aria-label, its associated <label>, or its visible text is what a human would call it, and therefore what a user's instruction will refer to.

What gets discarded

Styling, class names, data attributes, tracking pixels, and the entire text of navigation and footer regions are dropped. So are elements that are present in the DOM but invisible on screen, which an agent must never target.

Stable element identifiers

Each retained element receives a short identifier such as e12, assigned in document order and held in a map from identifier back to the live node. The model references only these identifiers. It never writes a CSS selector, and never sees one.

This is a security property as much as an ergonomic one. An identifier can only name something the extractor already decided was visible, enabled and interactive, so the set of actions reachable by a compromised planner is bounded by what a user could have clicked themselves.

Working within a context budget

Dense pages exceed any reasonable budget, so elements are ranked before truncation. Search inputs and submit buttons outrank decorative links; visible outranks hidden; labelled outranks anonymous. The surviving set is then restored to document order, so that positional phrasing in a user's request still lines up with the page.

Measured trade-offs

Representation Typical size Contains layout noise
Raw HTML Hundreds of kilobytes Yes
Stripped text Tens of kilobytes Partially
Semantic snapshot A few kilobytes No

The sizes above describe the shape of the trade-off, not a benchmark. Real figures depend entirely on the page.
